# Отчет по заданию 2.1 "Создание и развертывание статического сайта"

## Аннотация

В рамках выполнения задания разработан статический сайт с использованием генератора статических сайтов MkDocs на базе языка программирования Python. В репозитории подготовлена конфигурация автоматизированного развертывания на платформе GitHub Pages посредством системы непрерывной интеграции и доставки (CI/CD) GitHub Actions. Рассмотрен механизм деплоя \"Static HTML\" через экшены upload-pages-artifact и deploy-pages. Проведено исследование возможностей использования отечественных CDN (Content Delivery Network) для ускорения доставки контента, а также проанализированы возможности GitVerse для реализации CI/CD и варианты деплоя статических сайтов в продакшен-среду с указанием необходимых технических инструментов.

**Ключевые слова:** статический сайт, генератор статических сайтов, MkDocs, Python, GitHub Pages, CI/CD, GitHub Actions, автоматизация деплоя, CDN, GitVerse.

## 1. Введение

Статические сайты представляют собой веб-ресурсы, состоящие из предварительно сгенерированных HTML, CSS и JavaScript файлов, которые не требуют серверной обработки при каждом запросе. Данный подход обеспечивает высокую производительность, безопасность и простоту развертывания. Для создания статических сайтов используются специализированные инструменты — генераторы статических сайтов (Static Site Generators, SSG).

В качестве генератора статических сайтов выбран MkDocs — инструмент на базе Python, ориентированный на создание документации из файлов Markdown. Преимуществами MkDocs являются простота конфигурации, поддержка темы Material Design, встроенный поиск и возможность расширения функциональности через плагины. Выбор MkDocs обусловлен его интеграцией с экосистемой Python, что упрощает автоматизацию процессов сборки и деплоя.

## 6. Автоматизация деплоя: GitHub Actions -> GitHub Pages (Static HTML)

Процесс автоматизации деплоя реализован посредством GitHub Actions — встроенной в GitHub системы CI/CD. Конфигурация workflow определена в файле `.github/workflows/actions.yml`.

### 6.1. Структура pipeline

Workflow состоит из двух основных задач (jobs):

1. Job "build": выполняется сборка статического сайта.
2. Job "deploy": выполняется публикация собранного сайта на GitHub Pages.

Job \"deploy\" зависит от успешного завершения job \"build\" (параметр needs: build) и запускается только при push в ветку main (условие if: github.event_name == 'push' && github.ref == 'refs/heads/main').

### 6.2. Процесс сборки

Job "build" включает следующие шаги:

1. **Checkout:** получение кода из репозитория с использованием экшена `actions/checkout@v4`.
2. **Python Setup:** настройка интерпретатора Python версии 3.12 через экшен `actions/setup-python@v5`.
3. **Install dependencies:** обновление pip и установка зависимостей (MkDocs и тема оформления).
4. **Build:** выполнение команды `mkdocs build --strict` для генерации статических файлов в директории `site/`.
5. **Upload Pages artifact:** загрузка содержимого директории `site/` как артефакта для GitHub Pages с использованием экшена `actions/upload-pages-artifact@v3`.

### 6.3. Механизм "Static HTML"

Ключевым аспектом деплоя на GitHub Pages является использование механизма "Static HTML", который реализуется через два экшена:

- **`actions/upload-pages-artifact@v3`:** упаковывает статические файлы (HTML, CSS, JavaScript) из директории сборки в специальный артефакт, предназначенный для публикации на GitHub Pages. Параметр `path: ./site` указывает директорию, содержимое которой будет опубликовано.

- **`actions/deploy-pages@v4`:** развертывает загруженный артефакт на GitHub Pages. Экшен автоматически определяет URL опубликованного сайта и делает его доступным через переменную `steps.deployment.outputs.page_url`.

Данный подход отличается от альтернативного метода деплоя через ветку `gh-pages`, так как не требует создания отдельной ветки и обеспечивает более прозрачный процесс публикации через CI/CD.

### 6.4. Настройка прав доступа

Для корректной работы деплоя в секции `permissions` workflow определены следующие права:

- `contents: read` — чтение содержимого репозитория.
- `pages: write` — запись на GitHub Pages.
- id-token: write — генерация токенов для аутентификации (требуется для deploy-pages).

## 7. Исследование по вопросам технического задания

### 7.1. Возможности использования отечественных CDN для ускорения доставки контента

CDN (Content Delivery Network) — распределенная сеть серверов, предназначенная для доставки контента пользователям с минимальной задержкой за счет географической близости узлов к конечным пользователям.

**Архитектура интеграции CDN:**

Интеграция CDN с статическим сайтом включает следующие компоненты:

1. **Origin-сервер:** исходный источник контента (в данном случае — GitHub Pages или альтернативный хостинг).
2. **CDN-узлы (edge servers):** распределенные серверы, кэширующие контент и обслуживающие запросы пользователей.
3. **DNS:** система доменных имен, направляющая запросы к ближайшему CDN-узлу.
4. **Кэширование:** механизм хранения статического контента на CDN-узлах для снижения нагрузки на origin-сервер.

**Технические аспекты интеграции:**

- Настройка DNS-записей (CNAME или ALIAS) для направления трафика на CDN-домен.
- Конфигурация правил кэширования через HTTP-заголовки (`Cache-Control`, `Expires`).
- Настройка сжатия контента (Gzip, Brotli) для уменьшения объема передаваемых данных.
- Настройка TLS/HTTPS для обеспечения безопасного соединения.
- Инвалидация кэша (purge) при обновлении контента.

**Критерии выбора CDN для российских проектов:**

1. Наличие точек присутствия (PoP) на территории Российской Федерации для обеспечения низкой задержки.
2. Соответствие требованиям Федерального закона № 152-ФЗ "О персональных данных" в части локализации данных.
3. Поддержка современных протоколов (HTTP/2, HTTP/3, QUIC).
4. Наличие защиты от DDoS-атак и WAF (Web Application Firewall).
5. Прозрачность тарификации и масштабируемость решения.

**Примеры отечественных CDN-провайдеров:**

1. **NGENIX:** российская CDN-платформа, запущенная в 2008 году, изначально ориентированная на ускорение статического контента. Предоставляет географически распределенную сеть с точками присутствия в России.

2. **T1 Cloud CDN:** отечественное CDN-решение для доставки и кэширования контента (характеристики сети, SLA и тарифные параметры определяются документацией и условиями провайдера).

3. **StormWall:** сервис CDN с функциями защиты от DDoS-атак, обеспечивающий быструю передачу данных независимо от местоположения пользователя.

4. **RackStore:** CDN-решение с более чем 20 точками присутствия, поддержкой HTTP/2, HTTPS, IPv6 и методами компрессии (Brotli, Gzip).

5. **CDNvideo:** специализируется на ускорении сайтов, предлагая интеграцию через плагины для популярных CMS и поддержку кэширования статического и динамического контента.

**Практический сценарий применения CDN для MkDocs:**

Для оптимизации доставки статического сайта, созданного с помощью MkDocs, рекомендуется следующий подход:

1. Размещение собранных статических файлов в Object Storage (например, S3-совместимое хранилище) или на VPS-сервере.
2. Настройка CDN для раздачи контента из Object Storage или VPS.
3. Конфигурация длительного кэширования для статических ресурсов (CSS, JavaScript, изображения) через заголовки `Cache-Control: max-age=31536000`.
4. Настройка короткого времени кэширования для HTML-файлов или использование механизма инвалидации кэша при обновлении контента.
5. Применение версионирования ассетов (например, добавление хеша к именам файлов) для обеспечения актуальности обновленного контента.

### 7.2. Возможности GitVerse для реализации CI/CD

GitVerse позиционируется как отечественная альтернатива GitHub с акцентом на соответствие российскому законодательству, в частности требованиям 152-ФЗ о локализации данных.

**Концептуальная модель CI/CD в GitVerse:**

GitVerse может предоставлять функциональность, сопоставимую по назначению с GitHub Actions, для автоматизации процессов сборки, тестирования и развертывания:

1. **Workflow-файлы:** конфигурация CI/CD определяется в файлах формата YAML (конкретные требования к расположению и формату определяются документацией GitVerse).

2. **Раннеры (runners):** агенты, выполняющие задачи CI/CD (механизм и варианты исполнения зависят от реализации платформы).

3. **Секреты (secrets):** механизм безопасного хранения чувствительной информации (токены доступа, ключи шифрования) для использования в workflow.

4. **Артефакты (artifacts):** возможность сохранения результатов сборки (например, статических файлов) для последующего использования в других задачах или для деплоя.

**Пример конфигурации CI/CD для MkDocs в GitVerse:**

```text
Сборка: checkout -> настройка Python -> установка зависимостей -> mkdocs build
Деплой: публикация артефакта (Pages) или синхронизация site/ на целевой хостинг (Object Storage/VPS)
```

**Преимущества использования GitVerse для российских проектов:**

1. Локализация данных на территории Российской Федерации.
2. Соответствие требованиям 152-ФЗ о персональных данных.
3. Возможность интеграции с отечественными облачными платформами (при наличии соответствующей поддержки у GitVerse и провайдера).
4. Независимость от зарубежных сервисов.

**Инструменты для деплоя из CI/CD:**

- **Rsync/SCP:** для деплоя на VPS-серверы через SSH.
- **AWS CLI / S3-совместимые CLI:** для синхронизации с Object Storage (например, Яндекс Object Storage, Selectel S3).
- **API/CLI провайдеров:** использование SDK и CLI-инструментов облачных провайдеров для автоматизации деплоя.

| Настройки | Settings/Pages, параметры публикации |

**Вариант 2: Object Storage + CDN**

**Описание:** размещение статических файлов в облачном хранилище объектов (S3-совместимое) с раздачей через CDN.

**Таблица 7.2 - Преимущества и недостатки варианта 2 (Object Storage + CDN)**

| Преимущества | Недостатки |
|---|---|
| Высокая масштабируемость и отказоустойчивость. | Требуется настройка DNS и TLS-сертификатов. |
| Экономическая эффективность (оплата за фактически использованный трафик). | Необходимость управления кэшированием и инвалидацией кэша. |
| Глобальное ускорение доставки контента через CDN. |  |

**Технические инструменты (примеры):**

| Категория | Примеры |
|---|---|
| Object Storage | S3-совместимое хранилище |
| CLI/автоматизация | AWS CLI (или аналоги), bash-скрипты, CI/CD pipeline |
| CDN/DNS/TLS | CDN-провайдер, DNS (CNAME), TLS-сертификаты (например, Let's Encrypt) |

**Пример команды деплоя:**

```bash
aws s3 sync ./site s3://bucket-name/ --delete
```

**Вариант 3: VPS/выделенный сервер + веб-сервер (Nginx/Apache)**

**Описание:** развертывание статических файлов на виртуальном или физическом сервере с использованием веб-сервера.

**Таблица 7.3 - Преимущества и недостатки варианта 3 (VPS + веб-сервер)**

| Преимущества | Недостатки |
|---|---|
| Полный контроль над серверной конфигурацией. | Необходимость управления серверной инфраструктурой и обеспечение безопасности. |
| Возможность кастомизации под конкретные требования. | Требуется настройка мониторинга и резервного копирования. |
| Отсутствие зависимости от сторонних платформ. |  |

**Технические инструменты (примеры):**

| Категория | Примеры |
|---|---|
| Веб-сервер | Nginx, Apache |
| Доставка/синхронизация | SSH/SCP, rsync |
| Эксплуатация | systemd, TLS (Certbot), мониторинг |

Примечание: конфигурация веб-сервера определяется архитектурой проекта; для статики типично задаются корневая директория, индексный файл, правила 404 и политика кэширования статических ресурсов.

**Пример команды деплоя через rsync:**

```bash
rsync -avz --delete ./site/ user@server:/var/www/site/
```

**Вариант 4: Контейнеризация и оркестрация (Docker + Kubernetes/Nomad)**

**Описание:** упаковка статического сайта в Docker-контейнер с веб-сервером и развертывание через систему оркестрации.

**Таблица 7.4 - Преимущества и недостатки варианта 4 (контейнеризация и оркестрация)**

| Преимущества | Недостатки |
|---|---|
| Высокая масштабируемость и отказоустойчивость. | Высокая сложность настройки и управления. |
| Изоляция зависимостей и воспроизводимость окружения. | Требуется инфраструктура для оркестрации (Kubernetes, Nomad). |
| Возможность горизонтального масштабирования. |  |

**Технические инструменты (примеры):**

| Категория | Примеры |
|---|---|
| Контейнеризация | Docker |
| Оркестрация/сеть | Kubernetes/Nomad, ingress controller |
| Поставка | container registry, CI/CD pipeline |

Примечание: контейнеризация статики обычно сводится к упаковке каталога site/ в образ с веб-сервером и развертыванию через оркестратор.

**Рекомендации по выбору варианта:**

- **Для простых проектов и документации:** платформы для статических сайтов (GitHub Pages, GitLab Pages).
- **Для высоконагруженных проектов с глобальной аудиторией:** Object Storage + CDN.
- **Для проектов с требованиями к локализации данных (152-ФЗ):** VPS в российском дата-центре или отечественный Object Storage + CDN.
- **Для корпоративных проектов с требованиями к масштабируемости:** контейнеризация и оркестрация.

### Приложение Б. Структура workflow для GitHub Actions

Основные компоненты конфигурации `.github/workflows/actions.yml`:

- **Триггеры:** `on: push: branches: [ main ]` — запуск при push в ветку `main`.
- **Права доступа:** `pages: write`, `id-token: write` — необходимые права для деплоя.
- Job \"build\": сборка статического сайта и загрузка артефакта через upload-pages-artifact.
- Job \"deploy\": развертывание артефакта на GitHub Pages через deploy-pages.

Условие `if: github.event_name == 'push' && github.ref == 'refs/heads/main'` в job "deploy" обеспечивает запуск деплоя только при push в ветку `main`, исключая запуск при создании pull request.
