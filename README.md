Выполнено создание статического сайта с использованием MkDocs (Python). Подготовлен процесс развертывания на GitHub Pages средствами GitHub Actions и рассмотрен механизм деплоя \"Static HTML\" (upload-pages-artifact, deploy-pages). Представлено исследование: отечественные CDN, возможности GitVerse для CI/CD, варианты продакшен-деплоя статических сайтов и требуемые инструменты.

---

В работе используется генератор статических сайтов MkDocs (Python), преобразующий Markdown-материалы в набор статических файлов для публикации. Целевой способ размещения - GitHub Pages с автоматизацией через GitHub Actions.

---

## Исходные данные и структура проекта

Проект организован как репозиторий Git с следующей структурой файлов:

- `mkdocs.yml` — файл конфигурации MkDocs, содержащий настройки сайта (название, URL, описание, тема, навигация, плагины).
- `docs/index.md` — главная страница сайта в формате Markdown, содержащая исследовательский материал по темам CDN, GitVerse и вариантам деплоя.
- `.github/workflows/actions.yml` — конфигурационный файл GitHub Actions, определяющий автоматизированный процесс сборки и деплоя сайта.

Конфигурация MkDocs (`mkdocs.yml`) определяет использование темы Material с поддержкой светлой и темной цветовых схем, навигационную структуру сайта и включение плагина поиска.

### Настройка GitHub Pages

1. Settings -> Pages: выбрать источник публикации GitHub Actions.
2. Убедиться, что workflow находится в `.github/workflows/actions.yml` и выполняется при push в ветку main.

### Проверка результата развертывания

Проверка результата развертывания выполняется следующими действиями:

1. В интерфейсе GitHub открыт раздел Actions; подтверждено успешное завершение workflow развертывания (статус success).
2. В Settings -> Pages подтверждено использование источника публикации: GitHub Actions.
3. Выполнена проверка доступности опубликованного сайта в браузере (URL предоставляется отдельно при сдаче).

## Автоматизация деплоя: GitHub Actions -> GitHub Pages (Static HTML)

Workflow `.github/workflows/actions.yml` выполняет сборку MkDocs и публикацию на GitHub Pages. Механизм \"Static HTML\" реализуется связкой: upload-pages-artifact (загрузка каталога `site/` как артефакта Pages) и deploy-pages (развертывание артефакта). Для деплоя используются права pages: write и id-token: write.

## Исследование по вопросам технического задания

### Возможности использования отечественных CDN для ускорения доставки контента

CDN (Content Delivery Network) применяется для ускорения доставки статического контента за счет кэширования на распределенных узлах. Типовая интеграция включает origin (источник контента), DNS-маршрутизацию, политику кэширования (Cache-Control), TLS и инвалидацию кэша при обновлениях.

Критерии выбора для РФ-аудитории: наличие PoP в РФ, соответствие требованиям 152-ФЗ (при обработке персональных данных), поддержка современных протоколов и защитных функций (DDoS/WAF), прозрачная тарификация.

**Примеры отечественных CDN-провайдеров:**

1. **NGENIX:** российская CDN-платформа, запущенная в 2008 году, изначально ориентированная на ускорение статического контента. Предоставляет географически распределенную сеть с точками присутствия в России.

2. **T1 Cloud CDN:** отечественное CDN-решение для доставки и кэширования контента (характеристики сети, SLA и тарифные параметры определяются документацией и условиями провайдера).

3. **StormWall:** сервис CDN с функциями защиты от DDoS-атак, обеспечивающий быструю передачу данных независимо от местоположения пользователя.

4. **RackStore:** CDN-решение с более чем 20 точками присутствия, поддержкой HTTP/2, HTTPS, IPv6 и методами компрессии (Brotli, Gzip).

5. **CDNvideo:** специализируется на ускорении сайтов, предлагая интеграцию через плагины для популярных CMS и поддержку кэширования статического и динамического контента.

Практический сценарий: размещение статики в Object Storage или на VPS и раздача через CDN; для ассетов задается длительное кэширование, для HTML - короткое или применяется инвалидация при обновлениях.

### Возможности GitVerse для реализации CI/CD

GitVerse рассматривается как Git-платформа с возможностью построения CI/CD: workflow (YAML), раннеры, секреты, артефакты. Сценарий для MkDocs: сборка (mkdocs build) и деплой (публикация артефакта Pages или синхронизация каталога site/ на целевой хостинг). Для российских проектов потенциально важны локализация данных и соответствие требованиям законодательства.

### Варианты деплоя статического сайта в продакшен-среду и необходимые технические инструменты

Развертывание статических сайтов в продакшен-среду может осуществляться различными способами, каждый из которых имеет свои преимущества и требования к инфраструктуре.

**Вариант 1: Платформы для статических сайтов (GitHub Pages, GitLab Pages)**

**Описание:** специализированные платформы, предоставляющие хостинг статических сайтов с автоматической интеграцией CI/CD.

**Таблица - Преимущества и недостатки варианта 1 (Pages-платформы)**

| Преимущества | Недостатки |
|---|---|
| Простота настройки и отсутствие необходимости управления серверной инфраструктурой. | Ограниченная кастомизация серверной конфигурации. |
| Автоматическая интеграция с системой контроля версий. | Зависимость от экосистемы конкретной платформы. |
| Бесплатное использование для публичных репозиториев (GitHub Pages, GitLab Pages). |  |

Технические инструменты (примеры): CI/CD платформы, задачи деплоя, настройки публикации.

**Вариант 2: Object Storage + CDN**

**Описание:** размещение статических файлов в облачном хранилище объектов (S3-совместимое) с раздачей через CDN.

**Таблица - Преимущества и недостатки варианта 2 (Object Storage + CDN)**

| Преимущества | Недостатки |
|---|---|
| Высокая масштабируемость и отказоустойчивость. | Требуется настройка DNS и TLS-сертификатов. |
| Экономическая эффективность (оплата за фактически использованный трафик). | Необходимость управления кэшированием и инвалидацией кэша. |
| Глобальное ускорение доставки контента через CDN. |  |

Технические инструменты (примеры): Object Storage, CLI синхронизации, CDN, DNS, TLS.

**Пример команды деплоя:**

```bash
aws s3 sync ./site s3://bucket-name/ --delete
```

**Вариант 3: VPS/выделенный сервер + веб-сервер (Nginx/Apache)**

**Описание:** развертывание статических файлов на виртуальном или физическом сервере с использованием веб-сервера.

**Таблица - Преимущества и недостатки варианта 3 (VPS + веб-сервер)**

| Преимущества | Недостатки |
|---|---|
| Полный контроль над серверной конфигурацией. | Необходимость управления серверной инфраструктурой и обеспечение безопасности. |
| Возможность кастомизации под конкретные требования. | Требуется настройка мониторинга и резервного копирования. |
| Отсутствие зависимости от сторонних платформ. |  |

Технические инструменты (примеры): Nginx/Apache, SSH, rsync/scp, TLS, мониторинг.

Примечание: конфигурация веб-сервера определяется архитектурой проекта; для статики типично задаются корневая директория, индексный файл, правила 404 и политика кэширования статических ресурсов.

**Пример команды деплоя через rsync:**

```bash
rsync -avz --delete ./site/ user@server:/var/www/site/
```

**Вариант 4: Контейнеризация и оркестрация (Docker + Kubernetes/Nomad)**

**Описание:** упаковка статического сайта в Docker-контейнер с веб-сервером и развертывание через систему оркестрации.

**Таблица - Преимущества и недостатки варианта 4 (контейнеризация и оркестрация)**

| Преимущества | Недостатки |
|---|---|
| Высокая масштабируемость и отказоустойчивость. | Высокая сложность настройки и управления. |
| Изоляция зависимостей и воспроизводимость окружения. | Требуется инфраструктура для оркестрации (Kubernetes, Nomad). |
| Возможность горизонтального масштабирования. |  |

Технические инструменты (примеры): Docker, оркестратор, ingress, registry, CI/CD.

Примечание: контейнеризация статики обычно сводится к упаковке каталога site/ в образ с веб-сервером и развертыванию через оркестратор.

**Рекомендации по выбору варианта:**

- **Для простых проектов и документации:** платформы для статических сайтов (GitHub Pages, GitLab Pages).
- **Для высоконагруженных проектов с глобальной аудиторией:** Object Storage + CDN.
- **Для проектов с требованиями к локализации данных (152-ФЗ):** VPS в российском дата-центре или отечественный Object Storage + CDN.
- **Для корпоративных проектов с требованиями к масштабируемости:** контейнеризация и оркестрация.
